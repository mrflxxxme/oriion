# Definition of Ready (DoR) — контракт готовности фазы к автономному исполнению

> Нормативный чек-лист per [ADR-040 D1](../decisions/ADR-040-execution-spec-contract.md).
> `/autonomy:run` валидирует спеку фазы против этого списка **на discuss-шаге, до execute**.
> Провал любого пункта = фаза НЕ исполняется: раннер либо дорабатывает спеку сам (если пробел
> agent-owned), либо эскалирует (если пробел product/tripwire), и только затем продолжает.

## Чек-лист (все пункты обязательны)

| # | Требование | Проверка |
|---|---|---|
| 1 | **Goal** — одно предложение, проверяемый исход (не «улучшить», а «что появится/изменится») | Формулировка отвечает на «как узнаем, что готово?» |
| 2 | **Scope + Out-of-scope** — явные границы; всё соседнее названо и исключено | Каждое «не в этой фазе» имеет адрес (follow-up фаза / DEFERRED-VERIFICATION / RUNWAY) |
| 3 | **Acceptance criteria** — таблица `AC-NN.x | критерий | как проверяется`; каждый AC машинно- или evidence-проверяем | Нет AC вида «работает хорошо»; для каждого назван тест / гейт / evidence-артефакт |
| 4 | **Dependencies** — фазы/контракты/ADR, которые должны быть готовы; статус каждой проверен по факту (grep/git, не по памяти) | Все зависимости в статусе done/merged |
| 5 | **Founder-зависимости** — креды/решения из [`FOUNDER-RUNWAY.md`](../FOUNDER-RUNWAY.md), которые нужны фазе (или явное «нет») | Каждая — со статусом `ready`; иначе фаза паркуется (ADR-040 D7) |
| 6 | **Tripwire-прогноз** — какие категории [`tripwire.yaml`](../../.claude/autonomy/tripwire.yaml) фаза предположительно заденет | Прогноз есть; ack-needed фазы планируются с учётом ожидания founder |
| 7 | **Evidence-гейты** — какие local-only гейты фаза обязана эмитить (adversarial audit / docker-integration / live-golden / judge-panel) | Список назван; для live-golden — обоснована контрольная ценность (ADR-040 D11) или явное N/A |
| 8 | **Live-golden бюджет** — ожидаемая стоимость live-прогонов фазы в $ (или N/A) | Число указано; суммарно вписывается в dev_team caps (soft $20/day) |
| 9 | **Мягкие AC** — если какой-то AC сознательно закрывается частично (stub/plumbing/flag-OFF), для него заведена запись в [`DEFERRED-VERIFICATION.md`](../DEFERRED-VERIFICATION.md) | Запись существует ДО merge (иначе блокирующий review-flag, ADR-040 D6) |
| 10 | **Риски** — ссылки на затронутые R-NN из `risks/REGISTER.md` | Хотя бы прогон по top-5 активных рисков |
| 11 | **ADR-refs** — решения, на которые фаза опирается; новые архитектурные развилки будут логироваться per ADR-037 D4 | Ссылки валидны |

## Seed-spec (минимум для фаз текущей волны)

Каждая фаза текущей волны имеет seed-spec файл `phases/NN.M-slug.md` (5–15 строк) с полями:
**Goal · Границы (in/out) · Ключевые ADR · Gating/Runway-зависимости · Evidence-гейты + live-golden бюджет · Заготовка AC-направлений.**
Seed дорастает до полной спеки на discuss-шаге фазы; DoR-валидация применяется к доросшей спеке.

## Кто и когда применяет

- **`/autonomy:discuss`** — прогоняет чек-лист после resolve всех форков, ДО эмиссии PLAN.md; результат фиксируется строкой `DoR: PASS (11/11)` в PLAN.md.
- **`/autonomy:run`** — не переходит к шагу Execute без `DoR: PASS` в PLAN.md.
- **planner-роль** — использует чек-лист как шаблон при JIT-генерации спеки.

## Что DoR сознательно НЕ требует

- Оценок в человеко-днях (исполнение автономно; стоимость меряется в $, пункт 8).
- Inline-скелетов кода (Wave-0 стиль) — код-детали принадлежат PLAN.md, не спеке.
- Полных спек будущих волн — направления волн N+2+ остаются таблицами PHASES.md.
