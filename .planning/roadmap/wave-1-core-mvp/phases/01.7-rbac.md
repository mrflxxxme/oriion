- **Decision (grilled + founder-approved 2026-07-03, DECISIONS-LOG):** **Option A (flat visibility).** All cell members see all cell artifacts (RLS is already by `cell_id`; Member = cell access). Owner vs Member differ only in RIGHTS, not content visibility. Admin/Viewer → Wave 2.

## Goal

Ship **enforcement** of the Owner/Member split on top of the already-scaffolded
RBAC data layer: a FastAPI permission guard that requires **Owner** for
billing + cell-management (member management, role assignment) + cell-delete,
while **Member** can create tasks and see everything in the cell. Plus the
**`artifacts.visibility` stub column** (default `'cell-shared'`, NOT enforced)
that enables per-artifact privacy (Option B) later without an ALTER-under-data.

**Key finding / fork:** two parallel role stores exist — `rbac.role_assignments`
(what `has_permission` reads, **empty**) and `multitenancy.cell_members.role_id`
(the **populated** store: Owner at register, editable via the cells router).
Enforcement is built on **`cell_members`** (see Decision record) — the correct,
populated authority for the flat cell-scoped model.

## Decision record

- **Enforcement authority = `cell_members`, not `role_assignments`** (DECISIONS-LOG 01.7 impl fork F1). `role_assignments` is unwritten dead-store in Wave-1; backfilling it would duplicate the role store and risk drift. `cell_members.role_id` is the store the bootstrap + cells router actually maintain. Reversible: `has_permission` (role_assignments path) is preserved for a future wave's workspace-scoped/delegated grants.
- **403 (not 404) on deny** — Option A = flat visibility: a Member legitimately sees the cell; they only lack the right. Hiding existence (404) would contradict flat visibility.
- **`visibility` = stub only** — default `'cell-shared'`, `'private'` forward-declared, NOT enforced. Mirrors the ADR-038 graft pattern; Option B is a later policy change, not an ALTER-under-data.

## Adversarial audit (2026-07-04, 3 lenses, refute-by-default)

- **SECURE ✅ PASS** (0 P0/P1): (a) **cross-tenant** — `has_cell_permission` reads `cell_members` through the RLS-scoped tenant session AND filters `cm.cell_id = :cell_id / cm.user_id = :user_id`; a caller can only ever match their own cell's membership, so no cross-cell/cross-tenant grant leak. (b) **privilege-escalation** — default-deny: non-member OR role-without-grant → no row → 403; verified by `test_non_member_denied` + editor-deny integration test. (c) **injection** — the cross-context SELECT is fully parametrised (`:cell_id/:user_id/:slug`), no interpolation (`test_query_is_parameterised`).
- **SOUND ✅ PASS**: the guard is a hard `dependencies=[...]` side-effect that raises before the handler body runs — no bypass path (a handler cannot execute past a raising dependency). Reads intentionally ungated (flat visibility) — asserted open for both roles.
- **NO-REGRESSIONS ✅ PASS**: full unit suite 956 green; the pre-existing `billing_api_e2e` + `cells_router` suites updated to supply the guard deps and stay green (owner path exercises the guard for real). Migration is additive with a default → existing artifacts rows unaffected (table also empty in Wave-1).
- **P2/P3 / follow-ups:** see PLAN §Follow-ups.
