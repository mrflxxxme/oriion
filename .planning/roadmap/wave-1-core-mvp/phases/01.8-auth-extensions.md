## How the TOTP secret is stored at rest + how the second factor gates

- **At rest:** enroll calls `KMSProvider.encrypt(secret)` (LocalAESKMS,
  AES-256-GCM: `nonce||ct||tag`) and persists only the `bytea` ciphertext in
  `totp_credentials.secret_encrypted`. Decrypt happens in-memory at
  verify/confirm time. The base32 plaintext leaves the service exactly once (the
  enroll response) and is never logged. Backup codes are SHA-256 hashed.
- **Login gate:** `AuthService.login` verifies the password first; if the user
  has an ACTIVE credential (`confirmed_at IS NOT NULL AND disabled_at IS NULL`)
  it returns a `TotpChallenge` (short-lived HS256, `type=totp_challenge`,
  type-guarded so it can never be an access token) — **no session is minted on
  the password leg**. `login_totp` verifies the challenge + a live TOTP or
  single-use backup code before issuing the pair.
