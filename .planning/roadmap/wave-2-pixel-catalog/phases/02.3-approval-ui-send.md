# Phase 02.3 — Approval-UI + разблокировка human-approved send (seed-spec)

> Seed-spec per [DoR](../../DEFINITION-OF-READY.md). Закрывает главный незакрытый хвост W1: capability-gate режет все DANGEROUS-инструменты (01.9b «deny-until-approval-UI»), approval-UI так и не был построен — агенты навсегда read+draft. Первый полный цикл ценности «агент подготовил → человек подтвердил → ушло».

- **Status:** ⏳ Pending · **Queue:** после 02.2 (строится на DS v0.3)

**Goal:** пользователь получает веб-очередь «На подтверждение»: черновики исходящих действий агентов (telegram-пост, email) с полным текстом → approve/edit/reject → система реально отправляет; полностью автономный send остаётся выключенным.

**Scope (in):** очередь approvals (модель + API + UI-страница со списком/детальным просмотром/редактированием перед отправкой); переключение capability-gate: DANGEROUS `send_telegram_message`/`send_email` → approval-flow (deny → pending-approval → человек approve → исполнение); **каналы W2: только Telegram-пост (Bot API) + email (SMTP)** (D-08); **fail-closed scoping** (deferred-security из SECURE-аудита 01.9b — в скоуп); DLP-скрин черновика ПЕРЕД показом человеку + повторно перед отправкой; rate-limits на отправку; audit-строка на каждый approve/reject/send с actor; SSE/уведомление о новых pending-approvals.

**Out-of-scope:** autonomous send без подтверждения (W3+, отдельное решение с обязательным layer-A ML предусловием — D-08); layer-A ML DLP (deferred, компенсируется human-review + layer-B + rate-limits); Mini App как мобильный approve-фронт (W3, вместе с 01.11); другие каналы (yandex-disk write, WB — вне волны).

**ADR-refs:** ADR-041, ADR-014, ADR-039, ADR-030 (Mini App-часть — W3 revision).

**Gating/Runway:** RW-03 (Telegram bot-token + тест-канал) — нужен для live-proof отправки; без него фаза code-complete на mock, live-доказательство фиксируется DV-записью. Tripwire-прогноз: `public_api_contracts` (новые эндпоинты) + `db_migrations` (таблица approvals) + возможно `secrets_keys_crypto` → ack-needed.

**Evidence-гейты:** **adversarial-аудит обязателен** (SECURE-линза: невозможность обойти approve; injection в черновике не приводит к send; DLP-блок на ПДн в исходящем); integration real-PG (RLS на approvals); live-proof: реальный пост в тест-канал + реальное письмо через approve-флоу (при RW-03/RW-01). Live-golden бюджет: **~$0.5–1** (генерация черновиков живой моделью для e2e).

**AC-направления:** без approve НИ ОДИН send не исполняется (включая прямой вызов API — тест); edit-before-send сохраняет отредактированный текст как отправленный + аудит; reject возвращает задачу с фидбеком; DLP-находка в черновике блокирует send до ручного override с логом; rate-limit срабатывает; live: пост появился в тест-канале / письмо доставлено.
