## Section 01 — Code Review

**Verdict:** PASS-WITH-FIXES

Phase 00.6 PR-B is well-structured, atomically committed, type-strict, ruff-clean, and the 28 PR-B unit tests pass (`uv run pytest tests/runtime/test_dispatch.py tests/tasks/test_routers.py tests/scripts/test_demo_market_brief.py` → 28 passed). The inline-dispatch wiring is sound on the happy path and the seam design (injectable `leaf_specs`, version-tolerant `_extract_*` helpers, `ScriptedCoordinator` shaped like a Pydantic-AI agent) is genuinely good. **However there is one HIGH finding that would break the live 10× demo (AC9) and one HIGH finding that silently discards DB failure-state.** Neither is caught by the existing tests because the tests validate fabricated contracts, not the real ones. The anchor flip should not proceed until F-CR-1 is resolved (or the demo prompts are pinned), and F-CR-2 should be fixed-in-loop or explicitly pinned.

### Strengths

- **Atomic commit hygiene** — 8 commits, each scoped to one concern (C1 dispatch, C2 demo, C3 terraform, …), clear `[Phase 00.6 PR-B Commit N]` trailers.
- **Type-strictness** — `from __future__ import annotations` everywhere, keyword-only public signatures, `Decimal` for money (no float drift in cost math), explicit `# type: ignore[...]` with inline justification at every structural-shim seam (`dispatch.py:319`, `orchestrator.py:165`).
- **Version-tolerant Pydantic-AI bridge** — `_extract_output_text` / `_extract_usage` (`dispatch.py:103-133`) defensively handle `.output`/`.data` and `input_tokens`/`request_tokens` aliases, with direct unit coverage.
- **Honest documentation of deferred scope** — `dispatch.py` module docstring and `TaskNotDispatchable` docstring clearly mark what is Wave-0 deterministic vs. AC-W1-16 LLM-driven; no overclaiming.
- **Cost accounting is correct** (not a double-charge): leaf rows carry per-child `total_cost_credits`; orchestrator rolls the sum into the parent and `check_budget` only ever inspects `ctx.accumulated_cost` once per increment.
- **Exception envelope** — `TaskNotDispatchable` subclasses `TasksError`, which has a registered `app.exception_handler` (`main.py:306`) producing the RFC-7807 `problem+json` 409; the router test asserts the 409 + code.
- **Demo exit-code policy** — clean 0/1/2 separation (transport vs AC verdict vs pass) with strict-vs-tolerant latitude, well unit-tested.

### Findings

| ID | Severity | Finding | Suggested disposition |
|----|----------|---------|------------------------|
| F-CR-1 | HIGH | **Demo AC9 content-plan parser does not match the writer's actual output idiom — AC9 will read 0 posts and fail every live run.** `demo_market_brief.py:121` `_count_content_plan_posts` counts only `^\s*\d+\.\s+\*\*` (numbered list, bold-immediately-after). But the writer role-prompt's *canonical few-shot* (`.planning/contracts/role-prompts/writer.md:137-164`) steers the LLM to emit `### Пост 1 — Telegram — …` (H3 headers, no leading `N. **`). The dispatch sub-prompt framing (`dispatch.py:277-280`) says "контент-план ровно на 10 постов" but does **not** pin the `1. **` format. So the live writer output → `content_plan_posts == 0` → `ac9_passed == False` on all 10 runs. The unit test `test_count_content_plan_posts` passes only because `_content_plan_block()` (`test_demo_market_brief.py:42`) fabricates `1. **Пост i**` — i.e. the test validates the parser against a synthetic string that the real agent never produces. This is the classic "test asserts the wrong contract" trap. | fix-in-loop — either (a) loosen the parser to also count `^\s*###\s+Пост\s+\d+` / `^\s*\d+\.\s` and make the test feed the writer's real few-shot idiom, OR (b) pin the exact `1. **Пост N**` format in the writer sub-prompt framing in `dispatch.py`. Must be verified against a real run before the 10× gate. |
| F-CR-2 | HIGH | **Orchestrator failure-path DB state is silently rolled back.** On any exception inside `dispatch_task`, the orchestrator sets `task.status="failed"` + `completed_at` + cost on the session (`orchestrator.py:169-172`) and re-raises. That exception propagates out of `run_task` (`tasks.py:91`) — the explicit `await db.commit()` at `tasks.py:97` is never reached — through `get_db`'s `except Exception: await session.rollback()` (`session.py:55-57`). The `failed` status, `completed_at`, and any persisted child rows are **discarded**; the DB row remains `queued`. The SSE `task.failed` event (in-memory publisher) fires, so the stream and the DB now disagree. Wave-0 demo happy path is unaffected, but any provider failure / budget breach mid-demo leaves an inconsistent task row and no failure audit trail. | fix-in-loop if cheap (wrap dispatch in `try/except` in `run_task`, `await db.commit()` in the `except` before re-raising so the `failed` write survives), else Wave-1 pin AC-W1-16 (Dramatiq actor owns its own transaction boundary) — but document the gap explicitly. |
| F-CR-3 | MEDIUM | **Redundant double-commit + RLS-GUC teardown ordering.** `run_task` calls `await db.commit()` (`tasks.py:97`) while still inside the `set_tenant_context` CM and `get_db`'s yield; `get_db`'s `else: await session.commit()` (`session.py:59`) then commits again. The first commit ends the transaction and drops the three `SET LOCAL` RLS GUCs (`rls.py:59-60`). No DB access follows in this handler so it's currently harmless, but it's a latent footgun: any future code added after the dispatch in this handler would run under default-deny (no tenant GUC). The explicit commit is also semantically redundant with the dependency's own commit-on-success. | fix-in-loop — drop the explicit `await db.commit()` in `run_task` and rely on `get_db`'s commit-on-success (which also fixes F-CR-2's rollback-on-exception cleanly), OR keep it but document why and confirm nothing runs after it. |
| F-CR-4 | MEDIUM | **`ScriptedCoordinator` bypasses `delegate_task` tool guards.** It calls `deps.runner(...)` directly (`dispatch.py:223`), so the depth check + `target_agent_slug ∈ available_agent_slugs` validation in `delegate_task` (`delegate.py:114-129`) never runs for the Wave-0 path. The orchestrator's `runner_with_orchestration` wrapper does fire SSE delegation events + budget checks (so SSE/budget are fine), but an out-of-team slug or a pipeline longer than `max_delegation_depth` would not be rejected — only `build_leaf_runner`'s `KeyError` on an unknown slug catches it (as a 500, via the generic handler, not a typed 422). Acceptable for a hardcoded 3-step pipeline but it is a real divergence from the documented guard contract. | Wave-1 pin AC-W1-16 (real Coordinator routes through `delegate_task`); add a one-line note in `dispatch.py` that ScriptedCoordinator intentionally skips the tool guards. |
| F-CR-5 | MEDIUM | **`input_tokens` permanently zeroed in parent rollup.** `orchestrator.py:207` hardcodes `task.total_input_tokens = 0` and sums only `tokens_used` (output) into `total_output_tokens`. Yet `DelegateResult.tokens_used` is populated from `output_tokens` only (`dispatch.py:197`), while the child Task row *does* store the real `total_input_tokens` (`dispatch.py:187`). So parent `total_input_tokens` (0) ≠ sum of children's input tokens. The cost estimate (`estimate_credits`) *does* use both, so billing is right, but the token telemetry on the parent is misleading/inconsistent with children. The orchestrator docstring (`orchestrator.py:201-206`) acknowledges this as a deliberate Wave-0 simplification. | Wave-1 pin AC-W1-13 (real per-callsite billing + per-step token persistence); already documented, so confirm the pin is captured in 01.1-retro.md. |
| F-CR-6 | LOW | **`description=inp.sub_prompt[:255]` truncation is silent and mid-character-unsafe.** `dispatch.py:181` slices the Russian sub-prompt to 255 chars to fit the column; for Cyrillic this is a character slice (fine for `str`) but the truncation is silent — no ellipsis, no marker. Minor data-fidelity nit on the child-task audit row. | fix-in-loop (append `…` on truncation) or leave as LOW / Wave-1. |
| F-CR-7 | LOW | **`wait_healthy.sh` treats no-healthcheck containers as healthy.** `_all_ok` (`scripts/deploy/wait_healthy.sh:44-55`) passes any service reporting a bare `.State` (e.g. `running`) when it has no healthcheck — the self-test's `prometheus running` is classified OK. A container that is "running" but functionally broken (no healthcheck defined) would be deemed healthy and the deploy would proceed. Acceptable for staging, but it weakens the "all healthy" gate. | Wave-1 pin (AC-W1 deploy hardening) — or add healthchecks to all 9 compose services so every line reports `healthy`. |
| F-CR-8 | LOW | **Matrix-row counter is column-blind.** `demo_market_brief.py:109` `_count_matrix_rows` counts any `|`-line (minus header) but never verifies the ≥4-column requirement stated in AC9 ("≥5 строк × ≥4 колонки", per `dispatch.py:269`). A 2-column table with 6 rows would pass AC9's matrix check. Lower risk than F-CR-1 because the researcher prompt is steered to 4 columns, but the parser does not enforce the column dimension it claims to. | fix-in-loop (also assert `>= 4` pipe-delimited cells per row) or LOW accept. |
| F-CR-9 | LOW | **`get_task` ignores `cell_id` path scope (pre-existing, surfaced by review).** `get_task`/`run_task`/`cancel_task` all do `_ = cell_id` and rely solely on RLS for tenant scoping (`tasks.py:57,84,113`). A task from cell A is reachable via cell B's path as long as both are in the caller's RLS scope; the path `cell_id` is decorative. Documented as intentional ("routing scope"), and RLS does enforce tenant isolation, but the endpoint contract implies cell-level scoping it does not perform. | Wave-1 pin — add a `task.cell_id == cell_id` assertion (404 otherwise) for honest path semantics. Not PR-B-introduced; flag for completeness. |
