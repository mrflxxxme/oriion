# Judge-panel — wide-fork optimality (ADR-037 D5)

Most forks take a single pass (fast, cheap). A **wide fork** earns a judge-panel: generate N independent approaches, have the `evaluator` role rank them by a fixed rubric, take the winner and graft the best ideas from the runners-up. Expensive exploration only where it pays.

## When to trigger (wide-fork criteria)

Trigger the panel only if **all three** hold:

1. **The fork is agent-owned** (not escalated — see [`escalation-policy.md`](./escalation-policy.md)). Escalated forks go to the founder, not the panel.
2. **The solution space is genuinely wide** — architecture / algorithm / schema / data-flow choice where materially different designs exist (not "which of two equivalent spellings").
3. **The blast radius is high** — the choice is hard to reverse later (sets a schema, a public-ish seam, a cross-context contract) OR it dominates the phase's correctness/cost/perf.

If any is false → single pass with the recommended default. The planner flags wide forks in `PLAN.md` (`wide_fork: true`) so the runner knows to invoke the panel.

## Protocol

1. **Generate** N independent approaches (default **N=3**; N=2 for lower-stakes, N=4 for a schema/contract that will be very hard to change). Each approach is produced cold (no peeking at the others) so they diverge.
2. **Judge** — the `evaluator` role scores each approach against the rubric below. Refute-by-default posture: an approach must *earn* its score.
3. **Pick + graft** — take the top-ranked approach; explicitly fold in any superior sub-idea from the runners-up (name what was grafted).
4. **Record** — `log_decision.py --kind arch` (wide forks are ~always architectural) with the winner, the rubric scores, and what was grafted. Write/att­ach an ADR if it sets a precedent.
5. **Emit evidence** (D3 tie-in) — a judge-panel run writes `evidence/judge_panel_<fork>.json` (verdict `PASS` = a winner was chosen with a rationale; records the scores + cost). Declare it in `evidence/manifest.json` so `ci-evidence` can confirm the optimization actually ran against the merged commit — an auditable trail that "optimal" wasn't skipped.

## Rubric (fixed priority order)

The evaluator ranks lexicographically — a lower-priority dimension only breaks ties among approaches that are equal on the higher ones:

1. **Correctness** — does it actually solve the problem, handle the edge cases, preserve invariants (e.g. the billing `total == SUM(steps)`)?
2. **Security / integrity** — RLS/tenant isolation, secret handling, no new attack surface, data-integrity.
3. **Simplicity / maintainability** — least conceptual surface, fits existing patterns (ADRs), readable in a year.
4. **Cost** — token/compute/infra cost at runtime + dev-time (respects `cost-budget.yaml`).
5. **Performance** — latency/throughput, only where it matters.

> Correctness and security are gates, not trade-offs: an approach that loses on #1 or #2 cannot win by being simpler or faster.

## Cost discipline

The panel multiplies token spend on that fork (~N×). It is justified only by criterion #3 (high blast radius). The runner counts panel spend against the per-run budget (`cost-budget.yaml`, R-31); if the budget is tight, degrade N=3→N=2 before skipping the panel entirely on a truly wide fork.

## Roles used

`evaluator` (LLM-as-judge, ADR-023) does the scoring. The N approaches are generated by the relevant implementer role (`backend-implementer` / `frontend-implementer`) or, for pure design forks, `architect`. **Known gap:** these roles are handbooks, not yet spawnable subagents — the runner's role-prompt loader (Block C) wires the actual `Task` spawns. Until then the panel runs in-session (the main agent embodies each role from `.claude/agents/<role>/system-prompt.md`).
